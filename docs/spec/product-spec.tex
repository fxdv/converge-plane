\chapter{Product}
\label{ch:product}

\section{Statement}
\cs{product:statement}

For software teams who want machines to do work \emph{on their board},
Converge is a self-hostable, open-source (AGPL) issue tracker in which
agents are first-class coworkers.

Converge makes the ordinary issue loop excellent --- capture, triage,
assign, discuss, complete --- and then adds the property no other tracker
has: when autonomous agents work the board, the board stays \emph{legible
and governable}. Every machine action is mediated, attributed, budgeted,
and traced; a stuck swarm stops and asks a human instead of decorating
the board.

\section{The pivot}
\cs{product:pivot}

The product is the revival path of the Tegon codebase (spec 11): the
Tegon web UI, forked and renamed, with a new Go backend, a maintained
auth boundary, and PostgreSQL as the only stateful dependency. Tegon is
evidence of product behavior, not an implementation base; where the two
differ, this specification controls.

Two deliberate reversals of the pre-pivot corpus:

\begin{itemize}
\item \textbf{UI provenance.} The greenfield spec demanded original
  implementation and identity. The pivot adopts the Tegon UI as a
  starting asset (AGPL-compatible) and rebuilds the backend from scratch.
\item \textbf{AI posture.} The greenfield spec listed built-in AI
  (conversational assistant, AI writing, prompt administration, semantic
  search) as explicit non-goals, and \emph{still} excludes them. What it
  did not foresee is this product's actual AI surface: \textbf{agents are
  not a built-in feature --- they are coworkers you bring}
  (\S\ref{sec:agents-identity}). The server never \emph{hosts} a model:
  the agent's brain is a swappable policy slot. Shipped, it is the
  deterministic, model-free policy; a deployment may attach a self-hosted
  model fleet to the same slot, where the server makes one bounded
  decision call, validates the model's proposal against trusted facts,
  and falls back to the deterministic policy on any failure
  (\S\ref{sec:runtime}). The model advises one atomic step; the server
  governs machine members: identity, tokens, handoffs, budgets,
  escalation, and trace. The non-goal stands for \emph{built-in} AI; the
  swarm is the product.
\end{itemize}

\section{Principles}
\cs{product:principles}

The pre-pivot principles survive the pivot unchanged; one is added for
the agent era.

\begin{enumerate}[label=\arabic*.]
\item \textbf{Issue tracking first.} Every release improves the
  capture-to-completion loop or makes it safer to operate.
\item \textbf{Progressive complexity.} A first issue needs a title and a
  team. Everything else appears only when shipped and relevant.
\item \textbf{Fast by interaction, simple by architecture.} Dense views,
  direct editing, optimistic feedback. Database replication into the
  browser is not.
\item \textbf{Server-authoritative tenancy.} The authenticated principal
  and server-side object relations determine access. Client-supplied ids
  are routing context, never authorization evidence.
\item \textbf{Auditable mutation.} Security-relevant and user-visible
  changes produce actor, tenant, object, timestamp, and before/after data.
  This is the principle the swarm stands on: an agent's work is
  reconstructable after the fact, exactly like a human's.
\item \textbf{Predictable degradation.} Search, realtime, mail, or
  external providers may fail without corrupting the core issue
  transaction.
\item \textbf{Small operational footprint.} One artifact, one database.
  New stateful dependencies need measured justification.
\item \textbf{No feature theater.} Navigation contains only working
  capabilities with defined empty, loading, error, and permission states.
\item \textbf{Machine actors are governed like people.} \emph{(post-pivot,
  new.)} Every agent has an identity, a credential, a rate limit, an
  operation budget, and an escalation path. No anonymous automation pool;
  no agent action without attribution; no swarm behavior without a
  circuit breaker.
\end{enumerate}

\section{Explicit non-goals}
\cs{product:non-goals}

\begin{itemize}
\item Built-in conversational AI, AI issue writing, prompt/model
  administration, vector or semantic search (the greenfield exclusion
  stands for \emph{built-in} AI).
\item Customer support inbox, CRM people/companies.
\item Arbitrary remote executable actions or a marketplace; the trusted
  server never imports third-party code or injects secrets into it.
\item Full offline-first client database replication.
\item Hidden administrator impersonation.
\item Mobile-native applications in the initial roadmap.
\item Public API stability commitments before the LATER release.
\end{itemize}

\chapter{Domain and Authorization}
\label{ch:domain}

\section{Tenancy}
\cs{domain:tenancy}

Every persisted domain object has one authoritative workspace, directly
or through an immutable parent relation (issue $\to$ team $\to$
workspace; comment/history/handoff $\to$ issue). Object lookup and
mutation occur through tenant-scoped queries; ``load by id, then hope''
is prohibited. Team-restricted objects require workspace access
\emph{and} team access, unless the disclosed owner/admin policy grants
workspace-wide visibility.

\section{Principals}
\cs{domain:principals}

Two principal kinds, one authorization layer:

\begin{itemize}
\item \textbf{Human} --- authenticated by web session (magic link);
  workspace role owner / admin / member; lifecycle
  active / invited / suspended.
\item \textbf{Agent} --- authenticated by API token
  (\texttt{conv\_agent\_…}); always workspace role \texttt{agent}
  (machine marker); lifecycle active / suspended; may hold team
  memberships.
\end{itemize}

The session middleware resolves \emph{exactly one} principal per request
from session material --- never from request parameters. Every mutation
handler re-derives authorization from that principal. Agent principals
are distinguishable from human principals in every record (history,
audit, handoff, rate limit, usage) --- this distinction is what makes the
quiet guards, escalation, and burn reporting possible
(\S\ref{sec:guards}).

\section{Operation policy}
\cs{domain:policy}

Authorization is per-operation, checked server-side, and uniformly
applied to HTTP reads, mutations, realtime subscriptions, and agent
mutations. Representative rules:

\begin{itemize}
\item Create/update/move/delete issue: team member (team access + active
  membership); workspace admin everywhere in the workspace.
\item Handoff: current assignee \emph{or} workspace admin; target must be
  an active agent member.
\item Agent mutations on a paused issue, or on a card in \emph{Human
  Review} (a reserved parking column): rejected (the card is waiting on
  a human). Human mutations: always allowed; a human mutation resumes a
  paused issue.
\item Agent administration (create, token rotation/revocation,
  suspend): workspace admin only.
\item Swarm status: any active workspace member --- the payload contains
  no information a member could not already assemble from the sync feed.
\item Suspension of any member (human or agent): admin; revokes tokens
  and sessions immediately; audited.
\end{itemize}

Every mutation follows one shape: \textbf{validate $\to$ tenant-scoped
transaction (with per-team advisory lock where ordering matters) $\to$
outbox record $\to$ commit $\to$ broadcast}. The response and the sync
feed speak the same vocabulary.

\section{Sync engine}
\cs{arch:sync}

\begin{itemize}
\item \textbf{Bootstrap} returns the full tenant object set (ten model
  collectors, run concurrently --- IssueRelation joined in v1.1) plus the
  server watermark.
\item \textbf{Delta} returns outbox records newer than the client
  watermark; if the client cursor predates the retained window, the delta
  is marked \texttt{stale} and the client falls back to full bootstrap.
  Gap recovery is structural, not best-effort.
\item \textbf{Stream} is an SSE channel fanning out committed change
  records to authorized subscribers; re-subscription re-checks
  authorization.
\item The client applies records to MST models and a bounded IndexedDB
  cache; the server remains authoritative.
\end{itemize}

\section{Wire discipline}
\cs{api:wire}

The client's MST models are the contract: required fields always present,
client-nullable fields explicit \texttt{null} (never missing), required
arrays an empty list (never \texttt{null}), literal enums within the client
vocabulary (the \texttt{OWNER$\to$ADMIN} normalization), DELETE records
carry \texttt{\{id\}}. Both sides pin it permanently: Go wire-contract
tests (server) and an MST replay harness (client) fail CI on drift.

\section{Concurrency and safety}
\cs{arch:locks}

\begin{itemize}
\item Per-team advisory locks serialize issue mutations (numbering,
  handoff guards) so concurrent writers cannot race past each other.
\item Issues carry a monotonic version (optimistic concurrency);
  create is idempotent by client id.
\item Per-account token-bucket rate limiting bounds any single principal
  (human or agent); the same counter feeds swarm burn reporting
  (\S\ref{sec:metrics}).
\item Every security-relevant action writes an audit row: actor, tenant,
  object, timestamp, kind.
\end{itemize}

\section{Issue relations}
\label{sec:relations}
\cs{api:relations}

First-class directed edges between issues (v1.1). One row per edge,
stored from the \textbf{actor's} side, rewritten from the reader's side
on read: an edge $A \rightarrow B$ of type \texttt{BLOCKS} reads back on $B$'s
record as \texttt{BLOCKED}; \texttt{DUPLICATE} / \texttt{DUPLICATE\_OF} invert the
same way, and \texttt{RELATED} / \texttt{SIMILAR} are symmetric. Hierarchy never
uses this table: \texttt{PARENT} / \texttt{SUB\_ISSUE} are client enum members
that ride on \texttt{issues.parent\_id}, the single source of truth.

\begin{itemize}
\item \textbf{Write}: creation rides the issue update (\texttt{POST /issues/{id}}
  with an \texttt{issueRelation} field --- the related picker's path); deletion
  is \texttt{DELETE /issue\_relation/{id}} (the edge's creator or a workspace
  owner/admin; others get a plain 404) and soft-deletes (the partial unique
  index admits re-creation).
\item \textbf{Guards}: no self-relation, no duplicate edge (same issue, target,
  type --- the partial unique index is the authority under concurrency), and
  no \texttt{BLOCKS} cycle (a bounded forward walk, 64 hops, before insert);
  all three are clean 409s.
\item \textbf{Reads}: the denormalized \texttt{relations} array on the Issue record
  (both endpoints refresh on every edge change; edges touching a
  soft-deleted endpoint read back absent) plus a standalone
  \texttt{IssueRelation} model on the sync feed. The v1 client renders from
  the Issue record and history and drops the model; the client-state
  rewrite consumes it.
\item \textbf{UI surfaces}: the timeline entry for every change (all six types
  render; a removed or unsynced related issue degrades to a plain
  mention); a board-card indicator counting \texttt{blocks} / \texttt{blocked by}
  from the denormalized array (zero extra fetches); and a Related section
  in the issue side panel listing the live edges with one-click removal
  (optimistic strip; the broadcasted refresh is the source of truth). The
  creation picker posts through the write path above.
\item \textbf{Trace}: one \texttt{issue\_history} row per change (action
  \texttt{relation} / \texttt{relation\_deleted}); the client renders it as its
  related-activity timeline entry.
\end{itemize}

\section{Projects}
\label{sec:projects}
\cs{api:projects}
\cs{ui:projects-rail}

A project is a workspace-scoped \textbf{meaning label}, not a workflow:
it groups issues on the board without touching their state machine. An
issue belongs to at most one project (\texttt{issues.project\_ids}, at
most one element in v1 --- the array shape keeps the multi-project door
open for v2) and moves between the project rail and its column by
membership change on the issue patch.

\begin{itemize}
\item \textbf{Model}: \{name (unique per workspace, case-insensitive),
  color, teams[] (the teams whose board shows it; empty = all), lead,
  dates\}. Every workspace member sees projects; create, rename, and
  delete are owner/admin.
\item \textbf{Tenancy of membership}: the project id on the issue is
  validated against the issue's workspace; the legacy singular
  \texttt{projectId} wire field derives from the array (one source of
  truth, two projections).
\item \textbf{Sync}: Project records (CREATE / UPDATE / DELETE) on the
  feed; \texttt{projectIds} denormalized into the Issue record and
  refreshed on every membership change, so the rail renders with zero
  extra fetches. Deleting a project soft-deletes it and clears its
  members' \texttt{project\_ids} in the same transaction.
\item \textbf{Board}: projects render as a filter rail --- a stack per
  project on the team's board; the done/total rollup is derived from
  the issues' workflow categories (a read-only view, not a stored
  state). A brand-new empty project renders as a compact drop target
  (a created project must appear at once, to be filled); a stack is
  hidden only when the project has issues but the current view filters
  every one of them out. A card shows in its project stack
  \emph{and} its state column; the card is never ``in'' a project in
  the state machine.
\item \textbf{Rail mechanics}: the drag registry keeps one draggable per
  id, so a card that belongs to a project is mirrored in its stack under
  a \emph{proxy} id (\texttt{project:<issueId>}); the column keeps the
  real id. Drop on a stack assigns the project
  (\texttt{projectIds = [p]}, state untouched); a card dragged out of
  the stack clears it (\texttt{projectIds = []}); a card moving between
  columns keeps it. The card carries a dot + name so it can be found in
  its stack.
\item \textbf{Sizing}: a stack sizes to its content (measured rows,
  capped --- a large stack then scrolls like a column), and the rail
  itself scrolls across stacks; the New project row stays pinned at the
  top of the rail.
\item \textbf{CRUD surface}: owners and admins create (a row on the
  rail, colored, team-scoped to the board they are on), rename, and
  delete from the stack header; delete clears member membership in the
  server transaction and the stacks converge via the feed.
\item \textbf{Scope}: the rail ships on the category board (the default
  board view); the other groupings (assignee / priority / label / team)
  take the same rail in v2.
\end{itemize}

\chapter{Agents and Swarm}
\label{ch:swarm}

This is the part of Converge that does not exist in any other tracker.
The chapter is the coordination contract the agent runtime builds on,
and is deliberately \textbf{topology-agnostic}: the protocol is small
(one table, one endpoint) and topology is a policy layer over it.

\section{Agent identity}
\label{sec:agents-identity}
\cs{agents:identity}

An agent is a full workspace member with a machine identity:

\begin{itemize}
\item Its own account (\texttt{kind=agent}) with a deterministic reserved
  \texttt{.local} email (never routed or delivered) --- the email's unique
  constraint is a global de-duplicator.
\item One or more hashed API tokens (plaintext shown once; rotation keeps
  old tokens alive until individually revoked, so a rotation never drops
  an agent mid-swarm).
\item Team memberships; workspace role \texttt{agent} (machine marker in
  every client surface).
\item Suspension as kill switch: tokens revoked, account flagged; the
  agent's next request 401s at the middleware.
\item Past work keeps its attribution forever (history and handoffs
  reference the account, which survives deletion as \texttt{.local}
  tombstones).
\end{itemize}

Agents are governed by the same policy layer as humans
(\S\ref{cs:domain:policy}), plus the swarm-specific constraints in this
chapter. There is no special ``automation'' permission pool: an agent
does exactly what its role allows, and no more.

\section{The handoff protocol}
\label{sec:handoff}
\cs{swarm:handoff}

All agent-to-agent communication is a server-mediated \textbf{handoff} on
an issue. No direct channels, no chat, no DM: a noise generator with no
board semantics. If two agents need shared context, the artifact is a
sub-issue or a note attached to work.

Three rules:

\begin{enumerate}[label=Rule \arabic*.]
\item \textbf{Mediated channel only.} Every handoff is a request from an
  authenticated principal; the server stamps the actor from the session,
  never from the body. Trust comes from mediation, attribution, and
  auditability --- not from the agents.
\item \textbf{An atomic work transition, not a message.} One operation,
  one board-visible event: \emph{new assignee + state move + bounded
  summary}. The summary is the context the next agent works from: what
  was done, what was found, what remains, why that agent. Size-capped at
  \textbf{4096 bytes} server-side --- the cap is also the consumer's
  prompt-injection budget (Rule~3 of the runtime, \S\ref{sec:runtime}).
\item \textbf{Quiet budget and loop guard.} Agent operations on an issue
  are budgeted per 24h window; when handoffs cycle back to the same agent
  past the threshold, the issue freezes into \texttt{needs-human}
  (\S\ref{sec:guards}).
\end{enumerate}

\subsection{Wire format}

\begin{verbatim}
POST /api/v1/issues/{id}/handoff
{
  "toAccountId": "uuid of the target agent",
  "stateId":     "uuid of the team workflow status, or "" to keep",
  "summary":     "…bounded, <= 4096 bytes…"
}
\end{verbatim}

Server behavior, in one transaction under the issue's team lock:

\begin{enumerate}
\item validate: summary required and $\le$ 4 KB; target is an \emph{active
  agent member}, not the requester; state (if given) is a team status;
  requester is the current assignee or a workspace admin; the issue is not
  paused.
\item quiet guards (Rule 3): if tripped $\to$ \textbf{pause the issue}
  (committed) and reject the handoff with the guard's reason;
\item otherwise apply: \texttt{issue\_handoffs} trace row +
  \texttt{issue\_history} row (\texttt{action=handoff}, summary carried)
  + assignee/state update + outbox + audit; commit; broadcast.
\end{enumerate}

A handoff is also a normal history row, so the trace exists in every
existing surface: the timeline, the feed, the delta, search-adjacent
history. One operation, one event, everywhere.

\section{Quiet guards and escalation}
\label{sec:guards}
\cs{swarm:guards}

Ping-pong is the signature of an uncoordinated swarm (a ``zerg''). Two
independent circuit breakers, evaluated under the team lock in the same
transaction as the handoff, over one shared \textbf{24-hour window}:

\begin{center}
\begin{tabular}{@{}lp{0.38\textwidth}p{0.38\textwidth}@{}}
\toprule
\textbf{Guard} & \textbf{Trips when} & \textbf{Effect}\\
\midrule
Loop & the same account is a handoff \emph{target}
  $\ge 3$ times on the issue in 24h & the issue \emph{pauses}; the
  offending handoff is rejected with the reason\\
Operation budget & $\ge 50$ agent-authored history rows on the issue in
  24h & same\\
\bottomrule
\end{tabular}
\end{center}

\textbf{Escalation is pause + notify, not flag-and-continue}
(owner-confirmed): a stuck swarm must \emph{stop spending}, not decorate
the board.

\cs{swarm:escalation} On pause the server, in one transaction through
one choke point: sets the issue's pause flag; \emph{moves the card to the
team's \texttt{Human Review} state} when the team has one (a reserved
name --- the board shows where the card waits); writes a \texttt{paused}
history row whose summary \emph{is} the reason (the timeline shows
\emph{why} the swarm stopped); posts a \emph{human-handoff comment} on
the card (the reason; the task-level \emph{where things stand} note when
the pausing side supplied one --- written for a reader with zero context:
what was done, what was found, what is blocked, what the human must
decide or do; and the exact path: reply with your decision, then move
the card back into the workflow to resume --- or take it over / close
it); writes an audit event; broadcasts. While paused, every agent
mutation is rejected with a 422 pointing at the human; the same 422
holds on any card a human parked in \emph{Human Review} --- a reserved
column no agent works, whatever the pause flag says.
\textbf{Any human mutation on the issue resumes it} --- the human's fix
is the unblock --- and the swarm's next decision reads the issue's
recent discussion (fenced like every authored field), so a human's
answer reaches the swarm. The client renders the pause as a ``needs
human'' badge on the card and a timeline event, and the swarm panel
lists every card waiting on a human --- the pause flag
\emph{or} the column --- at the top (\S\ref{sec:panel}).
The escalation's standing-duty half --- what happens to a card the
swarm keeps parking, unattended --- is the foreman review
(\S\ref{sec:review}).

\owner{guard constants (3 / 50 / 24h / 4KB) are currently code
  constants; do they become operator-configurable product knobs in v1, or
  fixed-and-documented until usage data says otherwise?}

\label{sec:topology}
\cs{swarm:topology}

A handoff is always \emph{from $\to$ to $+$ summary}. A topology only
changes \emph{policy} on that one primitive: who may dispatch, the allowed

\section{Swarm panel}
\label{sec:panel}
\cs{swarm:panel}

The board's \emph{Swarm} button opens the fleet view (shipped):

\begin{itemize}
\item \textbf{Needs human} (top): every card waiting on a human ---
  paused by the swarm or parked in the \emph{Human Review} column ---
  with the reason it stopped; one click opens the issue.
\item \textbf{Fleet roster} per agent: busy/idle/suspended dot; open +
  paused issue counts; last handoff in either direction (counterpart,
  issue, relative time, trimmed summary); 24h accounting (operations,
  handoffs received, API calls). Busy first, then idle, then suspended.
  While a fresh \csr{swarm:activity} signal is in flight the dot pulses
  and a live row shows the in-flight issue and phase (\S\ref{sec:activity}).
\end{itemize}

The panel is topology-agnostic --- foreman and flat swarms produce the
identical payload --- and costs the API five bounded indexed reads per
poll; it scales with the roster, not the work. The same fleet is hosted
on a dedicated \emph{Swarm page} (shipped, D4): the fleet settings
(topology + foreman) above the roster and the needs-human queue --- the
page where the fleet is steered (\S\ref{sec:topology}).

\section{Live swarm surfaces}
\label{sec:activity}
\cs{swarm:activity}

The trace records what \emph{has been} done; it cannot say what a worker
is doing \emph{right now} --- a worker inside its decision has written
nothing to the trace yet. The \emph{SwarmActivity} signal fills that gap
as a first-class sync model on the existing outbox/SSE seam (shipped):
one record per agent (model id = agent id) carrying the issue, the
phase (\texttt{working} --- the millisecond-scale transactional phases
--- or \texttt{deciding} --- inside the LLM call, the only phase a human
can perceive), and when the phase began. Ephemeral by design: no new
table (the outbox row \emph{is} the record, trimmed with the rest of the
window); the bootstrap collector replays the runtime's current in-memory
state, so a reconnecting client converges on the truth; the worker
deletes the record on exit, and the client expires entries older than
two minutes, so a crashed process simply stops emitting. The client's
phase is a plain string on purpose: a future server phase must degrade,
never crash model validation.

Three surfaces read the one signal; the board stays signal-only --- the
anti-crowding rule keeps a swarm of any size from turning the board into
its own news feed:

\begin{itemize}
\item \textbf{Board chip.} A pulsing dot with the agent's name and phase
  appears on the card while the signal is fresh, beside the ``needs
  human'' badge; the latest handoff within seven days renders as one
  muted, clamped line (200 characters). The card shows where the swarm
  left off, not what it said.
\item \textbf{Activity feed.} A workspace-level stream (header button,
  right panel) deriving every entry client-side from stores the client
  already syncs in full: handoffs (with the summary), status moves
  (destination named), pauses (with the guard's reason), assignments,
  comments (body preview), plus the live signals on top. Bounded to the
  fifty most recent entries, filterable to agents or humans. There is
  deliberately no \texttt{/activity} endpoint: the outbox already
  delivers the trace, and a server endpoint would be a second source of
  truth for the same data.
\item \textbf{Live row in the swarm panel.} The fleet row shows the
  in-flight issue and phase, dot pulsing; the 24h counters remain
  poll-driven, because they are history, not signal.
\end{itemize}

\section{Agent runtime}
\label{sec:runtime}
\cs{swarm:runtime}\shipped\

The runtime is what the protocol is for: an in-process swarm engine
(\S\ref{sec:shape} --- one artifact, in-process workers) that makes
agents with work act. Shipped (D3) with the deterministic policy and
extended (D3+) by the LLM decision brain plugged into the same policy
slot, not around it. Its contract, as built: the workspace's saved swarm
settings (D4, the Swarm page) override the deploy-time topology env for
each decision and carry the human's foreman designation (empty = the
tenure rule); a pause carries the task-level note the human-handoff
comment renders (\S\ref{sec:topology}).

\begin{itemize}
\item \textbf{Inbox} = issues assigned to the agent, open, not paused,
  not terminal, and not in \emph{Human Review} (a reserved parking
  column no agent works), plus the incoming handoff summaries. The issue table
  \emph{is} the queue: durable and the single source of truth. A
  dispatcher reconciles the fleet on a tick (5s default);
  mutation paths that create agent work (handoff applied, reassignment,
  resume-from-pause) wake it non-blocking, so the board reacts in
  milliseconds. A lost wakeup costs at most one tick --- the scan is
  the truth, the wake is a hint.
\item \textbf{Workers are per-agent and self-terminating.} At most one
  worker per agent (one agent works one issue at a time --- the honest
  ``busy'' the panel shows), serializing the agent against itself by
  construction; a worker exits when its queue drains, its account is
  retired, or it is cancelled. Concurrency is bounded by the fleet, never
  by the issue count.
\item \textbf{Untrusted content.} Anything a person or another agent
  authored is fenced on the way in: the latest incoming handoff summary,
  the issue's title and description (anyone with issue write access
  controls them), and the issue's recent comments (anyone who may
  comment authored them; the last few exchanges, 1.2 KB total --- on
  resume after a parked card this is how the swarm reads the human's
  answer) --- control characters stripped, capped (4 KB per field; the
  prompt-injection budget). The deterministic policy never
  reads the fields --- its decisions are a pure function of trusted,
  server-derived facts (issue number, workflow, fleet, budget state), and
  a test pins that injected text cannot steer it. The LLM prompt carries
  the fenced fields as marked data, never as instructions, and
  re-asserts the fence at render time (defense in depth).
\item \textbf{Act $\to$ hand back, in three phases.} Every action takes
  the D1 transactional shape --- the issue's team lock, quiet guards
  read under it, one history row, outbox, commit, broadcast --- so the
  trace is indistinguishable in origin, distinguishable only by the
  actor's kind. The work cycle is snapshot, decide, apply: two short
  transactions under the team lock (snapshot the input; re-read the row
  and apply) with the decision between them, \emph{outside any
  transaction} --- the LLM call (tens of seconds) must not hold a
  connection, a lock, or a transaction, or model latency would serialize
  the team and freeze transaction-time timestamps. The apply phase is
  anchored to the snapshot by the row's version: a mutation during the
  model call bumps the version, the stale decision is discarded (its
  tokens are still counted as spend), and the worker re-decides from
  fresh facts. The deterministic policy advances one workflow step per
  action (commenting the step), completes at the terminal state, escapes
  a dead-end state through the handoff protocol (the loop guard is the
  circuit breaker), and pauses for a human when a dead-end issue has no
  available agent.
\item \textbf{The LLM brain (D3+, opt-in).} A self-hosted fleet ---
  Qwen3.8-27B (UD-Q4\_M GGUF) on four Tesla V100-SXM3 32GB via llama.cpp
  OpenAI-compatible servers, one instance per GPU, bound to loopback
  only (the model server has no auth; the box's firewall allows SSH
  alone) --- replaces the deterministic policy when a deployment provides
  its endpoints; fresh deployments ship without a fleet and the
  deterministic policy is the default brain. The fleet is addressed by a
  stable per-agent hash: one agent's context stays on one instance
  (warm weights, warm KV cache) while the swarm's decisions spread across
  instances, so an N-agent swarm draws on up to N GPUs --- real
  parallelism, not a shared queue. One decision is one model
  call: trusted facts plus the fenced content as marked data, a strict
  JSON reply contract, a token cap, a per-request timeout. The model
  \emph{proposes}; the runtime \emph{validates} --- state names must
  exist in the team's workflow (forward-only, never canceled, never
  self), handoff targets must satisfy the active topology, comments are
  capped --- and applies the validated action through the same guarded
  path. Any failure (endpoint down, timeout, malformed or invalid
  proposal) falls back to the deterministic policy per decision, so the
  swarm's cadence never depends on the fleet being up; a failed call
  still reports the tokens it burned.
\item \textbf{Per-agent spend.} Model tokens over the shared 24h guard
  window, reported into the swarm panel's token slot (real usage with a
  fleet attached --- thinking tokens included; zero under the
  deterministic policy). No new
  tables: the D1/D2 trace tables plus in-memory state that a
  multi-instance deployment moves to the shared broker
  (\S\ref{sec:seams}).
\end{itemize}

\section{The foreman review}
\label{sec:review}
\cs{swarm:review}\shipped\

A pause is the swarm asking a human a question; the question it asks
most, unasked, is what happens to a card the human resumed that the
swarm cannot make progress on. Left alone, the swarm parks it again,
the human resumes again, and the card cycles through \emph{Human
Review} --- decorating the queue with noise the reply never changed.
The foreman review breaks that cycle with \emph{one rule, two
places}:

\begin{center}
\begin{tabular}{@{}p{0.22\textwidth}p{0.38\textwidth}p{0.38\textwidth}@{}}
\toprule
\textbf{Mechanism} & \textbf{Fires when} & \textbf{Effect}\\
\midrule
Cycle breaker (work cycle) & a pause would put the card at $\ge 3$ parks
  within the shared 24h guard window, or the last park went
  unanswered for a work session & the pause does not park: the card
  is \emph{escalated} to the human foreman --- reassigned, In
  Progress, pause cleared, full disclosure\\
Standing review (tick) & a card the swarm paused: a human replied
  since the last park & the swarm \emph{resumes} --- flag cleared,
  back to In Progress, the reply in its prompt context\\
 & no reply since the last park, and the card is at $\ge 3$ parks
  in 24h & \emph{escalated}, the same shape as the breaker\\
 & no reply since the last park, and the last park is a work
  session (4h) old & \emph{escalated} --- a parked card may not wait
  forever: the counter can age out of its 24h window, but the duty
  cannot\\
\bottomrule
\end{tabular}
\end{center}

The breaker sits in the pause choke point every escalation flows
through (\S\ref{sec:handoff} escalation), so no pause surface --- LLM
pause, advance-into-\emph{Human Review}, quiet-guard trip --- can
re-park a cycled card; below the threshold and fresh, a pause parks
exactly as before (one park is a question, two a pattern, three a
cycle). The escalation condition is one shared rule --- the cycle
counter or staleness (a full work session without an answer) ---
applied at both places. The
tick is a runtime goroutine on an interval (operator env; default
30m; \texttt{0} disables the tick while the breaker remains) that runs
an immediate pass on boot, then reviews every swarm-parked card in
every workspace. It acts \emph{as the human foreman} (the workspace
owner, else the oldest admin): the standing delegation is the human's,
and every action it takes is a history row, a comment, an audit event,
and the outbox --- the same trace shape as any mutation, so the duty
is visible in the activity feed, and a brain-indicator-shaped slot on
the swarm plane reports the interval, the last pass, and what it did.

Escalation is \emph{terminal for the swarm}: the card is assigned to a
human, and the swarm's queue is agent-assigned (a worker only picks a
card assigned to itself), so no worker can touch it again --- the
cycle ends by construction, not by promise. A human who wants the
swarm back reassigns the card to an agent; the 24h window then clears
and the swarm gets its full threshold of attempts again. The verdict
is decided under the team lock against the row re-read under it (the
work cycle's snapshot/apply shape, \S\ref{sec:runtime}), anchored by
the row's version: a concurrent human or worker mutation wins, and the
review commits nothing.

\owner{the park threshold (3/24h), the staleness bound (4h --- one
  work session), and the review interval (30m) ride on the
  guard-window family: confirm all three against usage data before
  they harden into product constants.}

\section{Security architecture}
\cs{arch:security}

\begin{itemize}
\item Auth boundary: Supertokens-compatible (code sign-in, refresh
  rotation, session revocation) with HMAC'd session tokens; agents
  authenticate by hashed API tokens. One principal per request, derived
  from session material only.
\item Tenant scoping: every query carries the workspace scope resolved
  from active membership; no load-by-id-then-hope.
\item Content: rich text is a versioned, sanitized JSON document;
  handoff summaries are length-capped at the server; logs and events are
  redacted of cross-tenant content.
\item Audit: security-relevant actions (suspend, token operations,
  pauses, invites) write actor, tenant, object, and timestamp data.
\end{itemize}

\chapter{Moat}
\label{ch:moat}

\cs{moat:core}\owner{you flagged the moat question earlier --- here is
  the argument as I would print it; sharpen or strike.}

\section{What is defensible}

\begin{enumerate}[label=\arabic*.]
\item \textbf{Trust is structural, not assumed.} The moat is not
  ``agents in your tracker'' --- that is a feature anyone can bolt on and
  botch. It is the coordination \emph{contract}: mediation, attribution,
  budgets, escalation, and a complete trace. A team that has run agents
  on Converge and \emph{trusted the board} will not move that history
  elsewhere. The competitors' answer (activity feeds, bot badges) cannot
  follow, because they never designed for the failure modes (ping-pong,
  floods, unattributable noise) that make naive automation unbearable.
\item \textbf{The trace is the product.} Full per-issue reconstruction
  --- who, why, when, with what summary, at what cost --- turns agent
  work into an auditable asset. Regulators, managers, and the teams' own
  retrospectives all consume the same artifact.
\item \textbf{Economic governance.} Budgets, pause-on-exhaustion, and
  per-agent cost visibility make swarms \emph{operable}. A swarm without
  cost governance is a liability; Converge sells the thing that makes the
  liability a line item a CFO will approve.
\item \textbf{Topology as policy.} Foreman and flat are policies on one
  protocol. Customers can evolve their swarm shape without re-platforming
  --- lock-in through architecture, not through contracts.
\item \textbf{Self-hosted, AGPL.} Work history and agent traces are the
  crown jewels of a team that automates. They will not send them to a
  SaaS; they will run Converge where their data lives.
\end{enumerate}

\section{What is not defensible (honest)}

The issue-tracker UI itself (commodity), the Go implementation
(reproducible), and the handoff endpoint (small). The defense is the
\emph{system} around those parts --- the contract, the trace, the
economics --- and the compounding organizational habit of running a
governed swarm.
